## 2. 충돌 해결 프로토콜

### 2.1 충돌 인식

충돌이란: 두 에이전트가 같은 파일/기능을 다르게 해석하거나 수정하려는 상황

**자동 감지 신호**:
- 같은 파일에서 72시간 내 두 건 이상의 커밋
- 병렬 브랜치에서 `main`으로 병합 시 merge conflict
- benchmark 리포트에서 예상치 못한 결과 변화

### 2.2 충돌 해결 단계

**Step 1: 인식 및 보고 (충돌 당사자)**
- 충돌 감지 시 사용자에게 즉시 보고
- 형식: "충돌 감지: [파일:줄] [에이전트A] vs [에이전트B] / 원인: [간단히]"

**Step 2: 원인 분석 (당사자 + 사용자)**
- saju-expert & temple-db-engineer: benchmark 스크립트 결과 비교
- ui-deploy-engineer & 다른 에이전트: 코드 diff 리뷰
- 원인: (a) 의도적 변경인데 communication 미흡, (b) 회귀 버그, (c) 설계 해석 차이

**Step 3: 해결 방식 결정 (사용자)**
- **(a) Communication 미흡**: 재협의 후 한쪽이 자신의 변경을 (revert 또는 수정)
  - 변경 이유가 더 강하면 그쪽 유지, 다른 쪽 롤백
  - 둘 다 동등하면 사용자 판단
- **(b) 회귀 버그**: 최근 커밋부터 역순으로 bisect, 버그 주인공 담당 에이전트가 수정
- **(c) 설계 해석 차이**: 설계 문서 재검토 + 사용자 최종 판단

**Step 4: 코드 반영 (해결 담당 에이전트)**
- 합의한 방식대로 코드 수정
- 커밋 메시지에 `[충돌 해결]` 태그 + 원인·결정 한 문장
- 다른 당사자에게 알림

### 2.3 충돌 예방

**협업 체크리스트** (각 에이전트가 커밋 전 확인):

□ 같은 파일을 다른 에이전트가 최근 건드렸나? (git log 확인)  
□ 내 변경이 다른 도메인을 침범하나? (1.2 경계선 확인)  
□ benchmark 또는 테스트를 실행했나? (해당 스킬 사용)  
□ 변경 후 성능/결과가 의도대로인가?  
□ 커밋 메시지에 담당 범위와 의도가 명확한가?

## 3. 이슈 에스컬레이션 규칙

### 3.1 이슈 분류

**Level 1: 담당 범위 내 (자율 해결)**
- 자신의 도메인 파일만 관련
- 예: saju-expert가 matching-engine.js의 버그 수정
- 절차: 직접 수정 → benchmark 검증 → 커밋 → 사용자 보고 (이후)

**Level 2: 협업 범위 (요청 필요)**
- 다른 도메인 파일 수정 필요
- 예: saju-expert가 temple-db 스키마 변경 필요
- 절차: 사용자에게 이슈 리포트 → 담당 에이전트 요청 → 변경 후 영향도 재검증

**Level 3: 담당 범위 밖 (의존)**
- 자신의 도메인에서 버그/이상을 발견했으나 담당 에이전트가 다름
- 예: ui-deploy-engineer가 매칭 점수 이상을 발견 (saju-expert 담당)
- 절차: 최종 응답에 "🚨 이슈 리포트" 포함 → 사용자가 담당 에이전트 지시

**Level 4: 설계 재검토 필요 (사용자 판단)**
- 현재 설계가 애초에 잘못됐거나 요구사항 변경
- 예: 거리 가중치 배포 정책 변경
- 절차: 이슈 보고 + 설계 문서 인용 → 사용자 최종 승인

### 3.2 이슈 리포트 템플릿

각 에이전트는 담당 범위 밖의 이슈를 발견하면 최종 응답에 아래 형식으로 포함:

```
## 🚨 이슈 리포트

**파일**: <경로:줄번호>  
**증상**: <무엇이 잘못됐는지 한 문장>  
**심각도**: 
- 높음 (라이브 영향 / 사용자 피해)
- 중간 (잠재 버그 / 성능 저하)
- 낮음 (개선 사항)

**담당 제안**: [saju-expert | temple-db-engineer | ui-deploy-engineer | 사용자 판단]  
**근거**: <재현 방법 3줄 또는 코드 근거>

**제안 액션** (선택):
- 즉시 수정 필요
- 주간 동기화에서 논의
- 백로그 (우선도: P1/P2/P3)
```

### 3.3 에스컬레이션 권한

| 상황 | 결정권 | 절차 |
|------|--------|------|
| Level 1 이슈 | 담당 에이전트 | 자율 수정, 사용자 보고 |
| Level 2 요청 | 사용자 (승인) | 에이전트 제안 → 사용자 yes/no |
| Level 3 의존 | 담당 에이전트 (우선도) | 리포트 수신 → 우선도 판단 → 처리 일정 통보 |
| Level 4 설계 | 사용자 (최종) | 이슈 리포트 → 사용자 설계 검토 → 지시 |

## 7. FAQ & 트러블슈팅

**Q1: 에이전트의 커밋이 내 예상과 다른데?**  
→ 에이전트 정의 문서 (`.claude/agents/*.md`)의 "담당 파일" 섹션 재확인. 협업 범위라면 이슈 리포트 요청.

**Q2: 세 에이전트가 모두 관련된 문제는?**  
→ "주담당" 에이전트를 정하고 나머지는 "보조담당"으로 지정. 사용자가 최종 판단.

**Q3: benchmark가 실패하면?**  
→ 변경을 롤백하고 원인 파악. 버그면 수정 후 재실행. 의도적 변경이면 커밋 메시지에 명시.

**Q4: 배포 중 문제가 생겼는데, 누구 책임?**  
→ 빌드 실패 → ui-deploy-engineer / 점수 오류 → saju-expert / 검색 오류 → temple-db-engineer / 불명확 → 사용자 판단

**Q5: 우선도 충돌이 생기면?**  
→ 사용자가 우선도 결정. 에이전트는 제안만.

```
□ 검증 방법 제시 (어떻게 확인할 건지)
□ 필요하면 코드 예시 제시

예시:

```
