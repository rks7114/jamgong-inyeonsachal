# 오행 매칭 성능 테스트

`src/matching-engine.js` 변경이 (1) 성능 목표를 지키는지, (2) 추천 결과를 의도치 않게 바꾸지 않았는지를 한 번에 검증한다. 이 레포에는 별도 테스트 프레임워크가 없으므로 이 스킬이 사실상의 회귀 테스트다.

## 실행

레포 루트에서:

```bash
node .claude/skills/saju-test/scripts/benchmark.js
```

스크립트가 하는 일:
1. **테스트 케이스 자동 생성** — 결정적 시드로 matchTemples 10개, matchCoupleTemples 5개 (생년월일·목적·좌표 조합)
2. **결과 검증** — `git show HEAD:src/matching-engine.js`로 기준 엔진을 추출해, 케이스별 추천 사찰 `id:score` 목록이 현재 작업본과 동일한지 비교
3. **성능 실측** — 워밍업 2회 후 9라운드 측정, **최속 라운드**를 목표와 비교(중앙값 병기). 공유 컨테이너의 벽시계 노이즈가 판정을 흔들지 않게 하기 위함이다. (목표: matchTemples 11.7ms 이하, matchCoupleTemples 16.6ms 이하)
4. **벤치마크 리포트** — 마크다운 표 출력, 전부 통과 시 종료 코드 0

## 옵션

| 옵션 | 용도 |
|---|---|
| `--ref <커밋>` | 비교 기준 변경 (기본 HEAD). 예: `--ref HEAD~1`, `--ref main` |
| `--no-compare` | 동일성 검증 생략, 벤치마크만 (기준 커밋에 엔진이 없거나 처음 측정할 때) |
| `--target-single <ms>` `--target-couple <ms>` | 성능 목표 재정의 |
| `--tolerance <비율>` | 목표 대비 허용 오차 (기본 0.10 = 10%). 목표치가 최적화 당시 실측 평균이라 여유가 없어, 측정 노이즈로 판정이 뒤집히는 것을 막는다. `--tolerance 0`이 엄격 모드 |

## 결과 해석

- **결과 불일치 = 무조건 버그가 아님.** 스코어링 로직을 의도적으로 바꿨다면 불일치가 정상이다. 반대로 성능 최적화·리팩토링만 했는데 불일치가 나오면 회귀이므로 커밋하면 안 된다. 어느 쪽인지는 변경 의도를 기준으로 판단하고, 사용자에게 보고할 때 구분해서 말한다.
- **성능 목표(11.7ms/16.6ms)는 이 세션의 실측 기준값**이다. 다른 사양의 머신에서는 절대값이 다를 수 있으므로, 목표 미달 시 먼저 `--ref`로 변경 전 커밋을 같은 머신에서 측정해 상대 비교를 하라. 변경 전보다 느려졌는지가 절대값보다 중요하다.
- 엔진은 첫 호출에 캐시(validTemples 필터, templeKey)를 채우므로 워밍업 없는 1회 측정은 콜드스타트 비용이 섞여 부정확하다. 스크립트가 워밍업을 처리하니 직접 측정하지 말고 스크립트를 쓰라.

## 주의

- `npm install`이 되어 있어야 한다 (`lunar-javascript` 필요).
- 기준 엔진 임시 파일(`.baseline-*.tmp.js`)은 스크립트가 자동 삭제한다. 남아 있다면 이전 실행이 중단된 것이니 지워도 된다.
- 이 스킬은 매칭 품질(추천이 "좋은가")을 평가하지 않는다 — 성능과 결과 불변성만 검증한다.
