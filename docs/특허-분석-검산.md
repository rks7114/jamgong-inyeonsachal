# 특허 명세서 분석 · 검산 기록

다섯 건의 명세서를 받아 **수식을 직접 계산해 대조**하고, 책·코드와 어긋나는 지점을 정리한다.
검산은 손이 아니라 실행으로 했다. 재현 방법은 각 절에 적었다.

| 특허 | 명칭(약칭) | 책 대응 | 검산 결과 |
|---|---|---|---|
| ① | 방향성 관계행렬 + 편차 감쇠형 비가산 시너지 | 17~19장 | **전 항목 정합** |
| ② | 다중 이질 데이터 가중치 학습 · 택일 | 20장 | **불일치 5건** |
| ④ | 다중 모달 생체신호 · 감성 동기화 지수(SyncIndex) | 21장 · 부록F | **불일치 2건** |
| ⑤ | 다중 벡터 임베딩 · 상징 간 비가산 시너지(NCSI) | 21장 | 수치 실시예 없음 |
| — | 사주·천체력 기반 자동 작명(NCI) | 미수록 | **불일치 4건** |

우선심사신청설명서로 확인된 출원 1건: **10-2026-0094721**(천체력 트랜짓 → 라이프사이클 지표, 책 제16장).
고시 제4조제2호 **너목**(AI·빅데이터·맞춤형 헬스케어)으로 신청. 총 9건 출원.

## 1. 특허 ① — 검산 통과

### 1.1 실시예 재현

명세서의 모든 중간값이 수식 그대로 재현된다.

| 항목 | 명세서 | 재계산 |
|---|---|---|
| 결핍벡터 D | 0.333, 0, 0, 0, 0.333 | 동일 |
| raw | 0.47 | 0.4700 |
| E1 | 0.6214 | 0.6214 |
| 대상A L / G / Δ / S | 0.7759 / 0.7613 / 0.3786 / 0.1327 | 동일 |
| 대상B L / G / Δ / S | 0.7759 / 0.7368 / 0.5200 / 0.1076 | 동일 |
| CS_A / CS_B | 80.56 / 80.00 | 80.56 / 80.00 |
| 단순 가산 비교예 | 90.86 / 88.35 | 90.85 / 88.34 |

비교예 끝자리 0.01 차이는 반올림 자리이며 결론에 영향이 없다.

### 1.2 행렬의 일의성

25칸이 여섯 개 관계 규칙만으로 **분기 없이 재현**된다. 명세서가 "일의적으로 결정된다"고 쓴 대로다.

한 가지만 짚어 둔다. **"무관계 0.00"은 5×5 안에서 한 번도 등장하지 않는다.** 오행 다섯은 어떤 쌍이든 생 아니면 극 관계에 있기 때문이다. 규칙에는 있으나 실제 값이 없는 항목이므로, 성분이 여섯 이상으로 늘어나는 확장을 염두에 둔 조항으로 읽는 것이 맞다.

## 2. 특허 ① vs 인연사찰 엔진 — 다르다

명세서는 추천 대상에 **장소**를 포함하므로 인연사찰도 범위 안이다. 그런데 실제 엔진은 명세서와 상수도 결합 방식도 다르다.

| 항목 | 명세서 | 인연사찰 엔진 (`matcher.py` · `matching-engine.js`) |
|---|---|---|
| 동일 / 比 | +1.00 | +1.0 |
| 상생 / 生 | +0.60 | +0.6 |
| **역상생 / 洩** | **+0.30** | **−0.3** ← 부호 반대 |
| 역상극 / 耗 | −0.20 | −0.1 |
| 상극 / 剋 | −0.40 | −0.8 |
| 시너지 | γ·G·max(0, 1−δΔ), G=3요소 기하평균, γ=0.25, δ=0.80 | α·√(x_용·x_희), 2요소, α=0.15 |
| 편차 Δ | 적합도 요소 간 최대−최소 | **없음** |
| 과잉 처리 | CS = 100[L + S(1−L)] 잔여 구간 | g(x) = Kx/(K+x), K=40 (명세서에 없음) |
| 통합 | 가중합 L, Σw=1 | 보강 + 손상 + 시너지 합산 |

**결론:** 엔진은 명세서 **청구항 2의 범위 밖**이다. 청구항 2가 역상생을 "제3의 **양의** 값"으로 한정하는데 엔진은 음수를 쓴다.

### 2.1 "편차 감쇠"라는 이름 — 잘못 쓰고 있었다

가장 조용히 퍼져 있던 오류다.

- **명세서의 편차 Δ** = 여러 적합도 요소 사이의 **최대−최소 차이**. 요소가 고르게 높을수록 시너지를 키우는 장치.
- **책 제19장 2절 · 코드의 g(x)=Kx/(K+x)** = **한 오행이 과해지는 것**을 누르는 장치.

목적은 닮았지만 같은 것이 아니다. 그런데 특허 명칭에서 이름을 빌려 오면서 책 제19장 2절 제목, `matcher.py` 헤더·상수 주석·`damp()` 독스트링, `matching-engine.js` 섹션 헤더·상수 주석까지 전부 g(x)를 "편차 감쇠"라 부르고 있었다.

**조치 완료** — 책·코드 모두 "과잉 감쇠"로 정정. 제19장 5절 ④에 차이를 명시. `verify.py`에 재발 방지 검사 추가.

### 2.2 권고

**코드는 건드리지 않고 책을 사실에 맞춘다.** 이유:

1. 책의 수치는 전부 코드 실행으로 검증되어 있다(제18장 25칸, 제19장 최종 점수 3건). 상수를 명세서 쪽으로 옮기면 그 검증이 전부 무효가 되고 순위도 바뀐다.
2. 명세서 실시예 6이 "서비스 라인마다 매핑 테이블을 달리 보유"하는 확장을 이미 상정한다. 라인별로 상수가 다른 것 자체는 명세서 취지에 어긋나지 않는다.
3. 다만 **책이 둘을 같은 것처럼 적은 것**은 오도이므로 그것만 고친다.

## 3. 특허 ② (택일) — 보정 권고 5건

출원 전이거나 보정 가능한 단계라면 아래를 검토하시는 것이 좋겠다.

### 3.1 제1실시예 산술 불일치 ★

```
Syn_TU = √(0.42×0.21)×100×0.19 = 5.64   (명세서 3.44)
Syn_ST = √(0.37×0.42)×100×0.24 = 9.46   (명세서 4.87)
```

명세서 값을 역산하면 β₁≈0.116, β₂≈0.124가 나온다(명세서는 0.19, 0.24).
세 값의 합(72.4+3.44+4.87+5.0=85.71)만 맞아떨어져 **합산은 정합해 보이지만 시너지항이 수식에서 나오지 않는다.**

참고로 **제2실시예는 정확하다**(√(0.33×0.91)×100×0.30 = 16.44 ≈ 16.5). 제1실시예만 어긋난다.

### 3.2 W_Time의 정의가 세 갈래 ★★ — 가장 심각

같은 기호가 명세서 안에서 서로 다른 세 가지를 가리킨다.

| 위치 | 의미 | 값의 범위 |
|---|---|---|
| 구성 1 (Ridge Regression) | 학습되는 **중요도 가중치** | 학습 결과 |
| 구성 4 (f_season×f_day×f_ganji) | **곱셈형 품질 계수** | 0.648 ~ 1.872 |
| 실시예 1 (W합 = 1.00) | 합이 1인 **배분 계수** | 0.42 |

세 번째와 두 번째는 양립할 수 없다. 배분 계수라면 0.42가 맞고, 품질 계수라면 1.0 근처여야 한다.
**기재불비(명확성) 지적을 받을 수 있는 지점**으로 보인다.

### 3.3 Score_Final의 상한이 보장되지 않는다

부호의 설명은 `Score_Final: 0~100`이라 적혀 있으나, 수식상 최대 **126.5**까지 나올 수 있다(선형항 100 + 시너지 + Bonus 5).
클리핑이나 정규화 단계가 명세서에 없다.

> 특허 ①은 이 문제를 `CS = 100[L+S(1−L)]`로 구조적으로 풀었다. **같은 출원인의 두 명세서가 같은 문제에 서로 다른 완성도로 대응하고 있다.**

### 3.4 충돌 지수 CI의 정의가 역설적이다

```
CI = |Score(E_i) − Score(E_j)| × (1/Δt)
```

점수 **차이**에 비례하므로, **같은 날 점수가 똑같은 두 이벤트의 충돌 지수는 0**이 된다.
결혼식과 혼인신고를 같은 날 같은 점수로 잡으면 "충돌 없음"으로 판정된다. 근접도를 재려는 의도와 반대로 작동한다.

또 Δt→0에서 발산한다(같은 날이면 1/0).

### 3.5 제2실시예 CI 재배치 수치

`|91.8−88.7| = 3.1`. 7일 → 0.443, "+2일 재배치" 후 9일 → 0.344.
명세서의 0.41과 0.28이 나오려면 Δt가 각각 7.6일, 11.1일이어야 한다.

### 3.6 형식 사항

- **청구항 1의 `Bonus(O)`에 선행 정의가 없다.** 청구항만 읽으면 무엇인지 알 수 없다.
- **청구항 3이 "제1항 및 제2항"을 인용**하고, 제6·7·9항이 다시 그 제3항을 인용한다 → 다중종속항을 다중종속하는 구조. 심사 시 지적 대상이 될 수 있다.
- 청구항 3이 시스템 전체를 하나의 항에 담아 지나치게 길다.

## 4. 특허 ② — 서비스에 그대로 옮기면 안 되는 것 2건

특허의 **청구범위**와 서비스가 **화면에 띄우는 것**은 별개다. 아래 둘은 청구범위에 있어도 서비스에서는 하지 않는 것이 맞다.

### 4.1 수술 택일의 성공확률 (제4실시예)

**수술일을 사주로 고르고 성공확률을 숫자로 제시하는 것은 의료 판단 영역**이다.
이 책은 꿈해몽에서 "악몽이 반복되면 해석하지 말고 전문가 상담을 안내한다"는 선을 이미 그었다. 같은 선이 여기에도 적용되어야 한다.

**권고:** 서비스 이벤트 목록에서 수술의 성공확률·기대효용 출력은 제외. 날짜 후보 제시까지만.

### 4.2 손 없는 날 — 세 문서가 서로 달랐다

| 문서 | 입장 |
|---|---|
| 특허 ② | `Bonus(O)` **가산항으로 포함** (음력 9·10·19·20·29·30일) |
| 책 제20장 1·2절 | **근거 없음의 대표 사례**로 사용 ("손 없는 날과 달리 이 판정에는 근거가 있고, 사람마다 다르다") |

UI와 프롬프트가 **서로 모순**인 상태였다.

## 7. 특허 ④ (감성 동기화) — 불일치 2건

### 7.1 SyncIndex의 범위가 [0,1]이 아니다 ★★

명세서는 `SyncIndex(t)의 범위는 [0, 1]`이라 적고, 그 위에서 `T_low = 0.4`를 임계값으로 세운다.
그런데 수식에 값을 직접 넣으면 그 범위가 나오지 않는다.

```
SyncIndex = 0.6·Corr + 0.4·Sim − 0.1·(Corr × Sim)
Corr ∈ [−1, 1]   (피어슨 상관계수, 명세서 명시)
Sim  ∈ [0, 1]    (코사인 유사도, 명세서 명시)
```

| | 명세서 | 실제 |
|---|---|---|
| 하한 | 0 | **−0.60** (Corr=−1, Sim=0) |
| 상한 | 1 | **0.90** (Corr=1, Sim=1) |

정의역 전체를 훑으면 **31.3%의 조합에서 SyncIndex가 음수**가 되고, **67.6%가 T_low=0.4 미만**이 된다.
"0.4 미만이면 비동기화"라는 판정이 대부분의 정상 구간까지 잡아낸다는 뜻이다.

**보정 방향:** Corr을 `(Corr+1)/2`로 [0,1]에 사상하거나, 가중치 합이 1이 되도록 재설계하고 패널티항의 부호·계수를 조정해야 한다.

### 7.2 같은 명세서 안에 SyncIndex 수식이 둘이다 ★

| 위치 | 수식 |
|---|---|
| 과제의 해결 수단 (넷째) | `SyncIndex = ½ × (Corr + Sim)` |
| 모듈 4 (실시 내용) | `SyncIndex = 0.6·Corr + 0.4·Sim − 0.1·(Corr×Sim)` |

Corr=0.8, Sim=0.6을 넣으면 0.700과 0.672로 갈린다. 기재불비 소지가 있다.

### 7.3 기호 충돌

`A`가 한 명세서 안에서 **사용자 A**, **음향·언어 신호 A(t)**, **Attention(Q,K,V)의 인자**로 세 번 쓰인다.
`V`도 **시각 신호 V(t)**와 **Attention의 Value**로 겹친다.
`Z(t) = Attention(V(t), A(t), P(t))`는 읽는 사람이 Q·K·V 대응을 알 수 없다.

## 8. 자동 작명 특허 (NCI) — 불일치 4건

### 8.1 코사인 유사도가 계산되지 않는다 ★★★ — 가장 심각

핵심 수식이 `Cosine_Sim(V_Total, V_Name)`인데, 두 벡터의 차원이 다르다.

```
V_Total = V_S(5차원) + V_P(10차원) + V_Goal(차원 미정)   → 15+ 차원
V_Name  = V_Hanja(4) + V_Phon(3) + V_Semantics(3)        → 10 차원
```

코사인 유사도는 **같은 차원의 두 벡터**에서만 정의된다. 내적 `V_Total·V_Name` 자체가 성립하지 않는다.
명세서 어디에도 **차원 정렬·선형 투영·공통 임베딩 공간 사상** 단계가 없다.

> 참고로 특허 ①은 같은 문제를 **양쪽을 모두 5차원 오행 벡터로 강제**해서 풀었다.
> 작명 명세서는 그 장치 없이 이질 차원을 그대로 내적한다.

**보정 방향:** 특허 ⑤의 모듈 A처럼 `d_model` 공통 차원으로 선형 투영하는 단계를 추가하거나,
특허 ①처럼 양쪽을 5차원 오행 벡터로 축약한 뒤 방향성 관계행렬로 처리하는 구조로 바꾼다.

### 8.2 5격의 명칭과 정의가 무너져 있다 ★★

명세서가 적은 5격:

| 격 | 명세서 정의 |
|---|---|
| 원형(元格) | 성(姓) 첫 글자 획수 |
| 형격(亨格) | 성(姓) 전체 획수 합 |
| 이격(利格) | 이름(名) 전체 획수 합 |
| 정격(貞格) | 성+이름 전체 획수 합 |
| 총격(總格) | 성명 전체 획수 합계 |

두 가지 문제가 있다.

**① 정격과 총격이 같은 정의다.** "성+이름 전체 획수 합"과 "성명 전체 획수 합계"는 같은 말이다.
게다가 **외자 성이면 원형 = 형격**이 된다. 다섯 격 중 실제로 독립인 것은 **셋뿐**이다.

**② 명칭이 성명학의 것이 아니다.** 전통 성명학의 5격은 **천격(天格)·인격(人格)·지격(地格)·외격(外格)·총격(總格)**이다.
명세서의 원(元)·형(亨)·이(利)·정(貞)은 **주역 건괘의 사덕(四德)**이지 성명학 용어가 아니다.

청구항 6이 이 다섯 격을 그대로 인용하고 있어, 청구범위 해석에 직결된다.

### 8.3 O(n) → O(k log n) 주장에 근거가 없다 ★

- **가지치기**는 후보 수를 상수배로 줄이는 것이지 **차수를 낮추지 않는다.** (n → n/c 는 여전히 O(n))
- **KNN**은 인덱스가 있어야 로그 시간이 나온다. 전수 탐색 KNN은 O(n)이고, KD-tree·HNSW 같은 인덱스 구축은 그 자체로 O(n log n)이다.
- 명세서에 **인덱스 자료구조에 대한 언급이 전혀 없다.**

효과 항목에 "계산 복잡도를 O(n)에서 O(k log n)으로 감소"가 반복되므로, 근거가 되는 자료구조를 명시하는 편이 안전하다.

### 8.4 S_AB = S_A × (1+γ_AB)가 비대칭이다

A와 B의 **상호작용** 시너지인데 `S_A`만 곱한다. A와 B를 바꾸면 값이 달라진다.
또 이 `S_AB`가 `Score(N)`의 어느 항에 어떻게 들어가는지 수식에 나타나 있지 않다.

> 특허 ①의 `S = γ·G·max(0,1−δΔ)`는 기하평균이라 **대칭**이고, `CS = 100[L+S(1−L)]`로 **결합 위치도 명시**되어 있다.
> 같은 출원인의 두 명세서가 같은 문제를 서로 다른 완성도로 다루고 있다.

### 8.5 형식 사항

- **요약서에 청구항 13의 문장이 그대로 들어가 있다.** 발명의 요지가 아니라 기록매체 청구항 문구다. 편집 사고로 보인다.
- **청구항 3이 "알고리즘" 자체를 청구**한다. 순수 알고리즘은 발명의 성립성(제29조 제1항 본문) 거절 사유가 될 수 있다. 방법·시스템·기록매체 형식이 안전하다.

## 9. 작명 특허와 이 책의 원칙이 충돌한다 — 판단 필요 ★

두 지점에서 정면으로 부딪힌다. **기술 결함이 아니라 노선 문제**이므로 회장님 판단이 필요하다.

### 9.1 81수리 길흉

작명 명세서는 **81수리 길흉을 핵심 구성으로 청구**한다.

- `V_Hanja = [획수_정규화, 오행_인덱스, 음양_값, **81수리_길흉_점수**]`
- `NIV_score` = 5격 수리 **길흉** 점수 정규화값 → `Score(N)`의 세 항 중 하나(W3)
- 청구항 5·6이 이를 명시적으로 한정

그런데 81수리는 **획수만 같으면 누구에게나 같은 판정**이 나온다. 사주도, 용신도 보지 않는다.
이는 책이 제17장에서 "절대적으로 좋은 사찰은 없다", 제20장에서 "절대적으로 좋은 날도 없다"고 한 것과
**구조가 정확히 반대**다. 제20장 1절이 손 없는 날을 반례로 든 이유(문제 ② — 개인이 빠져 있다)가 그대로 적용된다.

| 선택지 | 내용 |
|---|---|
| **A** | 청구범위는 넓게 두되, **서비스는 81수리를 쓰지 않는다.** 책에는 작명을 싣지 않거나, 싣더라도 자원오행·음오행 매칭만 설명한다 |
| **B** | 서비스도 81수리를 쓰고, **책의 원칙을 수정한다** |
| **C** | 81수리를 **참고 표시로만** 내보낸다(손 없는 날과 같은 처리) |

**의견:** A 또는 C. 지금까지 삼재를 빼고 손 없는 날을 참고로 내린 판단과 일관되려면 그쪽이다.
B는 이 책의 1장부터 30장까지가 서 있는 자리를 무너뜨린다.

### 9.2 TEI 실시간 반영 — 이름이 조회한 날마다 바뀐다

명세서는 종래 기술의 문제로 **"조회 시점과 무관하게 항상 동일한 결과를 반환"**하는 것을 들고,
이를 "정적 예측 편향(Static Prediction Drift)"이라 부르며 TEI로 해결한다고 한다.
ΔTEI가 임계값을 넘으면 NCI를 재산출해 WebSocket으로 순위를 밀어 보낸다.

**그런데 이름은 평생 쓰는 것이다.** 같은 아기가 화요일과 목요일에 다른 이름을 추천받게 된다.

이것은 특허 ⑤가 효과로 내세운 **"동일 입력에 대해 일관되고 재현 가능한 구조화 출력"**과,
이 책이 제2장부터 요구해 온 **재현성·반증 가능성**과 정면으로 배치된다.
같은 입력에 매번 다른 답이 나오면 틀렸는지 확인할 방법이 없다.

**의견:** TEI는 **작명 결과가 아니라 "언제 개명 신고를 할지"** 같은 택일 성격의 출력에만 붙이는 것이 일관된다.
이름 후보 순위 자체를 실시간으로 흔드는 것은 재고가 필요하다.
